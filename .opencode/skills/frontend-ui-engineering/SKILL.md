# Frontend UI Engineering

## Goal

Build user interfaces that look like they were designed by a design-aware engineer, not generated by an AI. Every output must be accessible, responsive, and consistent with the project's existing stack and design system.

## When to Use

- Building new UI components or pages
- Redesigning existing interfaces
- Implementing responsive layouts
- Adding interactivity, state, motion, or visual polish
- Fixing visual or UX issues
- Auditing UI quality

## Required Context

Before designing, confirm:

1. **Target audience**: who uses this UI and in what context?
2. **Use cases**: what jobs must it support?
3. **Brand tone**: how should it feel?
4. **Existing stack**: framework, styling, component library, tokens.
5. **Existing design system**: fonts, colors, spacing, radius, elevation.

If missing, ask the user one concise question instead of guessing.

## Anti-AI-Aesthetic Discipline

Avoid these LLM defaults:

| AI Default | Why It Fails | Do Instead |
|---|---|---|
| Purple/indigo gradients | Every AI app looks identical | Use project's actual palette |
| Excessive rounded corners (`rounded-2xl`) | Ignores hierarchy of radii | Use design-system radius scale |
| Centered hero over dark mesh | Template-driven, no content fit | Content-first layout |
| 3 equal feature cards | Ignores information priority | Purpose-driven asymmetry |
| Lorem ipsum copy | Hides real layout problems | Realistic placeholder content |
| Oversized uniform padding | Destroys visual hierarchy | Consistent spacing scale |
| Inter + slate-900 | The generic AI default | Project-appropriate typography |
| Heavy drop shadows | Competes with content | Subtle or no shadows |

## Component Architecture

### File Structure

Colocate component files:

```
src/components/
  TaskList/
    TaskList.tsx          # Implementation
    TaskList.test.tsx     # Tests
    TaskList.stories.tsx  # Storybook (if used)
    use-task-list.ts      # Hook (if complex)
    types.ts              # Component types
```

### Patterns

- **Prefer composition over configuration.**
- **Keep components focused** — < 300 LOC per file; split when larger.
- **Separate data fetching from presentation.**
- **Avoid prop drilling deeper than 3 levels.**

## State Management Hierarchy

```
useState        → Component-specific UI state
Lifted state    → 2-3 sibling components share
Context         → Theme, auth, locale (read-heavy, write-rare)
URL state       → Filters, pagination, shareable UI state
Server state    → React Query / SWR / TanStack Query
Global store    → Zustand / Redux for complex client state
```

## Spacing and Layout

- Use the project's spacing scale. Do not invent values like `13px` or `2.3rem`.
- Mobile first. Test at 320px, 768px, 1024px, 1440px.
- Never use `h-screen`; use `min-h-[100dvh]` to avoid iOS viewport jumps.
- Wrap the page in `overflow-x-hidden` if off-screen animations are used.

## Typography

- One display font + one refined body font maximum.
- Build hierarchy with weight, color, and spacing — not size alone.
- Do not skip heading levels.
- Limit hero headline to 2-3 lines by widening container, not shrinking leading.
- Banned default fonts: Inter, Roboto, Arial, Open Sans, Helvetica unless the design system explicitly uses them.

## Color

- Use semantic tokens: `text-primary`, `bg-surface`, `border-default`.
- Ensure contrast: 4.5:1 for normal text, 3:1 for large text.
- Never rely on color alone to convey state.

## Accessibility (WCAG 2.2 AA)

### Keyboard

- Every interactive element must be focusable and activatable by keyboard.
- Prefer native `<button>`, `<a>`, `<input>`, `<select>`.
- If a `div` must be interactive, add `tabIndex={0}`, `role`, and keyboard handlers for Enter/Space.

### ARIA and Labels

- Label icon-only buttons: `aria-label="Close dialog"`.
- Associate labels with inputs via `htmlFor` + `id`.
- Use `role="status"` for live regions and empty states.

### Focus and Motion

- Manage focus on route/modal/dialog open.
- Trap focus inside modals.
- Honor `prefers-reduced-motion`: replace motion with instant state changes.
- Animate only `transform` and `opacity`.

## Loading, Error, and Empty States

Never leave a blank screen. Every async or list UI needs:

- Skeleton (not spinner for content)
- Error state with retry
- Empty state with next action

## Responsive Design

```tsx
// Tailwind mobile-first example
<div className="
  grid grid-cols-1
  sm:grid-cols-2
  lg:grid-cols-3
  gap-4
">
```

## Design System Adherence

1. Preserve existing tokens unless explicitly re-branding.
2. Use official packages for known systems (Fluent, Carbon, Primer, GOV.UK, USWDS, shadcn/ui).
3. One system per project. Do not mix.
4. If no system exists, create a minimal token file before writing components.

## Performance Guardrails

- GPU-safe animations only (`transform`, `opacity`).
- `backdrop-blur` only on fixed/sticky elements, never scrolling containers.
- Lazy-load below-the-fold images and heavy components.
- Keep components under 300 LOC.

## Verification Checklist

Before completing:

- [ ] Renders without console errors
- [ ] All interactive elements keyboard accessible
- [ ] Screen reader can convey content and structure
- [ ] Responsive at 320px, 768px, 1024px, 1440px
- [ ] Reduced-motion fallback works
- [ ] Loading, error, and empty states present
- [ ] Follows project design system
- [ ] No banned AI-aesthetic patterns
- [ ] Component files < 300 LOC or split
- [ ] Accessibility warnings from axe-core/dev tools resolved

## Red Flags

- Components > 200 lines
- Inline styles or arbitrary pixel values
- Missing error/loading/empty states
- Color as sole state indicator
- Generic AI look
- Unnecessary dependencies
